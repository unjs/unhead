This page is for framework authors. It lists what an integration does to use the [lazy head](/docs/vue/head/guides/core-concepts/lazy-head). The examples use Nuxt hook names.

Nuxt does not ship the lazy head. Nuxt owns its head integration, so this page describes no Nuxt option. A Nuxt module or a patch can add it with the steps below.

::note
The lazy head is experimental. Its API may change in a minor release.
::

The server side needs no change. The server keeps its head from `@unhead/vue/server`, and the client swaps its head for the lazy head.

## Replace the client head plugin

Nuxt adds its own client head plugin. Remove it, or the app gets two heads. A module can filter it out in `app:resolve` and add the lazy plugin in its place:

```ts
import { createResolver, defineNuxtModule } from '@nuxt/kit'

const NUXT_CLIENT_HEAD_RE = /head[\\/]runtime[\\/]plugins[\\/]unhead(?:-stream)?\.client/

export default defineNuxtModule({
  setup(_, nuxt) {
    const resolver = createResolver(import.meta.url)
    nuxt.hook('app:resolve', (app) => {
      const index = app.plugins.findIndex(plugin => NUXT_CLIENT_HEAD_RE.test(plugin.src))
      // A miss keeps the default client head with no sign, so fail the build instead.
      if (index === -1)
        throw new Error('Nuxt client head plugin not found. Update NUXT_CLIENT_HEAD_RE.')
      app.plugins.splice(index, 1, { src: resolver.resolve('./runtime/lazy-head.client'), mode: 'client' })
    })
  },
})
```

Set `mode: 'client'`. Nuxt does not read the `.client` suffix of a plugin that `app:resolve` adds. Without the mode, the lazy plugin also runs on the server. The server app then provides the lazy head, so code that reads the head through Vue's `inject`, such as `useScript` from `@unhead/vue/scripts`, puts its tags in a head the server never renders.

The pattern matches an internal Nuxt path, so check it on each Nuxt upgrade. The build fails when it no longer matches.

Import `@unhead/vue/lazy` and `@unhead/vue/plugins` from the `@unhead/vue` copy that Nuxt uses. A second copy puts unhead in the client bundle twice. In a monorepo, add aliases resolved from Nuxt's package, as Nuxt does for `@unhead/vue/plugins`.

## Create the lazy head

Create the head with `createHead()` from `@unhead/vue/lazy`. Pass the options of the default client head, such as `disableDefaults`. Push the app head as the default client head does. If the integration registers `TemplateParamsPlugin` on the client, pass it in `lazyPlugins`, so its code loads with the runtime.

```ts
import { createHead } from '@unhead/vue/lazy'
import { defineNuxtPlugin } from 'nuxt/app'
import { appHead } from '#build/nuxt.config.mjs'

export default defineNuxtPlugin({
  name: 'head',
  enforce: 'pre',
  setup(nuxtApp) {
    const head = createHead({
      disableDefaults: true,
      lazyPlugins: () => import('@unhead/vue/plugins').then(m => [m.TemplateParamsPlugin]),
    })
    head.push(appHead)
    nuxtApp.vueApp.use(head)

    // No server head to keep: load at once.
    if (!nuxtApp.isHydrating || !nuxtApp.payload.serverRendered)
      head.load()

    // Hold head updates until the app has mounted, and during each navigation, as the
    // default client head does. The pause also holds the load.
    let paused = true
    head.hooks.hook('dom:beforeRender', (ctx) => {
      if (paused)
        ctx.shouldRender = false
    })
    const resume = () => {
      paused = false
      head.render()
    }

    // Hydration has ended.
    nuxtApp.hook('app:suspense:resolve', resume)
    nuxtApp.hook('page:loading:start', () => {
      if (!nuxtApp.isHydrating)
        paused = true
    })
    nuxtApp.hook('page:loading:end', () => {
      if (!nuxtApp.isHydrating)
        resume()
    })
    // A pause that never lifts holds every head update, so lift it on an error too.
    nuxtApp.hook('app:error', resume)
  },
})
```

Call `head.render()` once hydration ends. Before that call, a hydrating component adds entries without a load.

The pause starts on. On a page with no server render, the runtime loads at once, but the page pushes its entries later. The pause holds the first render until the app has mounted.

Keep the rest of Nuxt's client head setup that your app relies on, such as deferring an entry dispose until a page transition ends.

## Load at once when no server head applies

The lazy head counts every entry before hydration ends as server rendered. If no server head applies, call `head.load()` right after you create the head. A load that no change started before hydration ends tells the head that no server head applies, so it adopts nothing. Without the call, the tags wait for a change, and a page with no server render shows no head until then. This applies in these cases:

- The page has no server render. In Nuxt, that is a page with `ssr: false` or an SPA fallback page.
- The head is created after hydration ended. An integration that creates the head on first use, so that an app with no client head call ships no head code, can create it during a navigation or in a client only plugin.

Nuxt sets `isHydrating` to `true` on every client boot, even with no server render. So check `payload.serverRendered` too, as the example does.

For a whole app with no server render, keep `createHead()` from `@unhead/vue/client`. It costs fewer bytes than the lazy head and its runtime together.

## Turn off prefetch hints

The lazy head loads its runtime, and the `lazyPlugins` chunk, through dynamic imports inside the `unhead` and `@unhead/vue` packages. Nuxt renders prefetch hints for the dynamic imports of the entry and turns them on once the app is ready. So without a change, the browser downloads the runtime right after hydration. Remove those imports from the entry's prefetch list:

```ts
const UNHEAD_CHUNK_RE = /[\\/](?:unhead|@unhead[\\/]vue)[\\/]dist[\\/]/

nuxt.hook('build:manifest', (manifest) => {
  for (const chunk of Object.values(manifest)) {
    if (chunk.isEntry)
      chunk.dynamicImports = chunk.dynamicImports?.filter(id => !UNHEAD_CHUNK_RE.test(id))
  }
})
```

## Pause the load during navigation

Pause head updates when a navigation starts, and lift the pause when it ends. A [`dom:beforeRender`](/docs/head/api/hooks/dom-before-render) pause holds the load too. Call `head.render()` after you lift it. If entries changed during the pause, the runtime loads then.

- Start the pause before the next page runs `setup()`. Nuxt's `page:start` fires too late: it runs after the new page's `setup()`. Use `page:loading:start`.
- Lift the pause on every path, including a failure or an error. In Nuxt, `page:loading:end` also fires when a navigation fails, and `app:error` fires on an error.
- If the router has no navigation hooks, nothing can pause the load. In Nuxt, `page:loading:start` and `page:loading:end` fire only when the app uses the pages integration.

Without a pause, the first step of a navigation loads the runtime while the next page still loads.

## Modules that push head tags

A module entry that changes on a navigation loads the runtime, as any other entry does. After hydration, each new push loads the runtime, even if its input matches an existing entry. A dispose loads it too. Only a patch with the same input as before loads nothing. So if a module keeps the same input across pages, keep one entry and patch it.

A `.client` plugin runs before hydration ends. A push in its setup counts as server rendered, so its tags wait for the first change. The same holds for a value that a component computes only on the client. If such a tag must show at once, call `head.load()` after the push. The dev warning names each one.

Most client hooks, such as a `tags:resolve` listener, take effect when the runtime loads. These hooks run before the runtime loads:

- `entries:updated` runs on each push and dispose, also during hydration. It runs on a patch only if the patch changes the input. A patch with the same input as before does not run it. During hydration, an in-place edit to the input does not run it either, because the lazy head treats the edit as server rendered.
- `dom:beforeRender` runs on each change after hydration, because the lazy head checks for a pause. Its `tags` list is empty.
- In development, the dev check resolves the tags once after hydration. So the resolve hooks, such as `tags:resolve`, run then.

## Recover from a failed load

If the runtime chunk fails to load, the document keeps its current head. A browser may keep the failed import for the page, so a later change can fail too. Pass `onLoadError` to recover, for example with a full reload on the next navigation.

Nuxt's default chunk error mode does not cover this import. It reloads on the next navigation only when that navigation fails on a chunk error.

## Streaming

Use the lazy head only for responses that do not stream. It does not support streaming SSR.

## Check the integration

Compare each page with the same page and the default client head. Run the network checks on a production build.

- Hydration must change no head element.
- On a server rendered page, the browser must not fetch the runtime chunk before the first head change.
- A navigation must hold the load until it ends.
- After each navigation, the whole head must match the default client head.
- A page with no server render must show its head.
- A head created after hydration must show the tags of its first entries.
- In development, the console shows a [dev warning](/docs/vue/head/guides/core-concepts/lazy-head#dev-warning) for each client tag that waits for a change. Fix each one, or call `head.load()` after hydration.
