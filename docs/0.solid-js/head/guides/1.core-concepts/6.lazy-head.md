On a server rendered page, the server already wrote the right head tags. The lazy head keeps head entries in memory and leaves those tags alone. The Unhead DOM runtime loads from a separate chunk on the first head change. A visit with no head change never loads it.

::note
The lazy head is experimental. Its options may change in a minor release.
::

This guide sets up the lazy head in a Vite SSR Solid app, as set up in the [installation guide](/docs/solid-js/head/guides/get-started/installation). The same steps fit any setup where your code calls `hydrate()`. Components need no change: `useHead()`, `useSeoMeta()`, and `useScript()` work as before.

Keep `createHead()` from `@unhead/solid-js/client` in these cases:

- The app renders on the client only.
- The app uses [streaming SSR](/docs/solid-js/head/guides/core-concepts/streaming). The lazy head does not support streaming.

## What the client entry provides

The lazy head needs three signals that only the client entry has:

| Signal | Call | If the call is missing |
| --- | --- | --- |
| Hydration ended | `head.render()` right after `hydrate()` returns | A push outside a component, such as from the client entry, counts as server rendered. Its tags wait for a change. Every change loads the runtime at once, even during a navigation pause. The dev warning never runs. |
| A navigation runs | A [`dom:beforeRender`](/docs/head/api/hooks/dom-before-render) pause, then `head.render()` when it ends | The runtime loads while the next page still loads. |
| No server head applies | `head.load()` right after you create the head | The first entries count as server rendered, so their tags wait for a change. A page with no server render shows no head until then. |

## Set up the client entry

The server entry keeps `createHead()` from `@unhead/solid-js/server`. Nothing changes there.

Create the head from `@unhead/solid-js/lazy` in its own module, and add the navigation pause there. Your router imports the navigation functions from this module. A router module also runs on the server, so it must not import the client entry.

```ts [src/head.ts]
import { createHead } from '@unhead/solid-js/lazy'

export const head = createHead()

// Pause head updates while a navigation runs. The pause also holds the load.
let navigating = false
head.hooks.hook('dom:beforeRender', (ctx) => {
  if (navigating)
    ctx.shouldRender = false
})

// Call this when your router starts a navigation.
export function startNavigation() {
  navigating = true
}

// Call this after the new page renders, and when the navigation fails.
export function endNavigation() {
  // With no navigation running, such as during hydration, do nothing.
  if (!navigating)
    return
  navigating = false
  head.render()
}
```

In the client entry, provide this head instead of creating one inside `hydrate()`. Then call `head.render()` after `hydrate()`:

```tsx [src/entry-client.tsx]
import { UnheadContext } from '@unhead/solid-js/lazy'
import { hydrate } from 'solid-js/web'
import App from './App'
import { head } from './head'

hydrate(() => (
  <UnheadContext.Provider value={head}>
    <App />
  </UnheadContext.Provider>
), document.getElementById('root')!)
// Hydration has ended.
head.render()
```

Solid marks the components that `hydrate()` runs against the server HTML. A push from such a component counts as server rendered. A push from `onMount()`, or from a component that mounts after hydration, cannot be in the server head. So it loads the runtime, even before `head.render()`.

A router can end its first navigation while `hydrate()` still runs. So `endNavigation()` does nothing when no navigation runs. Without that check, its `head.render()` call ends hydration early. The runtime then loads on every page.

To check the result, build the app and load a page with the network panel open. Hydration changes no head element. No Unhead runtime chunk downloads. On the first navigation, the runtime chunk downloads once the new page has rendered. The head then matches what the default client head shows.

## What loads the runtime

After hydration, the first head change loads the runtime. The runtime renders the whole head. It also handles every later change. A patch with an equal input is no change.

| Trigger | When the runtime loads |
| --- | --- |
| A signal change that patches an entry with a new value | At once, unless a pause holds it. |
| `useHead()` in `onMount()`, or in a component that mounts after hydration | At once, even before `head.render()`. After `head.render()`, a pause can hold it. |
| A patch or dispose during hydration | At once, because the client already differs from the server. |
| `useScript()` | When its script starts to load, even during a pause. With the default trigger, the script starts to load on mount. |
| `head.load()` | At once. Call it at idle to apply client only values without a change. |

Solid runs `createEffect()` during hydration. So an entry that starts empty and gets its values from `createEffect()` loads the runtime during hydration. Pass the initial values to `useHead()`, as the Signals example in [Reactivity](/docs/solid-js/head/guides/core-concepts/reactivity) shows.

The lazy head compares plain objects, lists, and primitive values. During hydration, `useHead()` patches its entry with its own input. The lazy head compares that input once hydration ends. A function value, such as `title: () => title()`, counts as a change. So it loads the runtime once hydration ends. Read [What loads the runtime](/docs/vue/head/guides/core-concepts/lazy-head#what-loads-the-runtime) in the Vue guide for the rules that compare input. They are the same for every framework.

## Dev warning

In development, the lazy head checks the tags the client would render against the server head after hydration. The console shows one warning for each tag that waits for the first change. The Solid adapter gives no component name to the lazy head, so the warning names the entry number:

```txt
[unhead] <meta name="rendered-by"> differs from the server head in content. Pushed by entry 1. It applies on the first head change. Push the same input on the server and the client, or call head.load().
```

Read [Dev warning](/docs/vue/head/guides/core-concepts/lazy-head#dev-warning) for what the check compares.

## Known limitations

| Situation | What happens | What to do |
| --- | --- | --- |
| A function value in the input of `useHead()` | It loads the runtime once hydration ends. | Pass values, and patch from `createEffect()`. |
| A `<Show>` or other branch that renders on the client only during hydration | In a production build, the head counts the entry of the branch as server rendered. Its tags wait for a change. In development, Solid throws a hydration mismatch error if the branch renders an element. If it renders none, the dev warning names the tag. | Render the same branch on both sides, or show the branch from a signal that `onMount()` sets. |
| A `<Suspense>` boundary that hydrates after `hydrate()` returns, such as one around a `lazy()` component | Its entries arrive after hydration ended, so they load the runtime. | None needed. The head stays correct, and the runtime loads early. |
| A value that the client computes differently from the server | The document keeps the server value until the first change. The dev warning names the tag. | Render the same value on both sides, or call `head.load()` after hydration. |
| The runtime chunk fails to load | The document keeps its current head. | Use the `onLoadError` option to recover, for example with a full reload on the next navigation. |
