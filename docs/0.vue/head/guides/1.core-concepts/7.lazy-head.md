On a server rendered page, the server already wrote the right head tags. The lazy head keeps head entries in memory and leaves those tags alone. The Unhead DOM runtime loads from a separate chunk on the first head change, usually the first navigation. A visit with no head change never loads it.

::note
The lazy head is experimental. Its options may change in a minor release.
::

This guide sets up the lazy head in a Vite SSR Vue app with Vue Router, as set up in the [installation guide](/docs/vue/head/guides/get-started/installation). The same steps fit any setup that hydrates a server render and owns its client entry. Components need no change: `useHead()`, `useSeoMeta()`, and `useScript()` work as before.

Keep `createHead()` from `@unhead/vue/client` in these cases:

- The app renders on the client only.
- The app uses [streaming SSR](/docs/vue/head/guides/core-concepts/streaming). The lazy head does not support streaming.
- A framework creates the head for you. The framework must adopt the lazy head itself.

## What the client entry provides

The lazy head needs three signals that only the client entry has:

| Signal | Call | If the call is missing |
| --- | --- | --- |
| Hydration ended | `head.render()` | A push outside a component, such as from a Vue plugin, counts as server rendered, so its tags wait for a change. The dev warning never runs. |
| A navigation runs | A [`dom:beforeRender`](/docs/head/api/hooks/dom-before-render) pause, then `head.render()` when it ends | The runtime loads while the next page still loads. |
| No server head applies | `head.load()` right after you create the head | The first entries count as server rendered, so their tags wait for a change. A page with no server render shows no head until then. |

## Set up the client entry

The server entry keeps `createHead()` from `@unhead/vue/server`. Nothing changes there.

In the client entry, replace `createHead()` with the one from `@unhead/vue/lazy`, and add the hydration and navigation signals:

```ts [src/entry-client.ts]
import { createHead } from '@unhead/vue/lazy'
import { nextTick } from 'vue'
import { createApp } from './main'

const { app, router } = createApp()
const head = createHead()

// Pause head updates while a navigation runs. The pause also holds the load.
let navigating = false
head.hooks.hook('dom:beforeRender', (ctx) => {
  if (navigating)
    ctx.shouldRender = false
})
app.use(head)

router.isReady().then(() => {
  app.mount('#app')
  // Hydration has ended.
  head.render()

  router.beforeEach(() => {
    navigating = true
  })
  // Lift the pause after the new page renders, and when the navigation fails.
  const done = () => {
    navigating = false
    head.render()
  }
  router.afterEach(() => nextTick(done))
  router.onError(done)
})
```

Call `head.render()` once hydration ends. Before that call, a `useHead()` call in a hydrating component adds an entry and loads nothing.

Vue Router calls `afterEach` before the new page renders. So the pause lifts in `nextTick()`, after the old page removes its entries and the new page adds its entries. A page that renders later, such as an async `setup()` inside `<Suspense>`, needs a later release: lift the pause when `<Suspense>` resolves. The [Pause DOM Rendering](/docs/vue/head/guides/core-concepts/pausing-dom-rendering) guide uses the same pause for the default client head.

To check the result, build the app and load a page with the network panel open. Hydration changes no head element, and no Unhead runtime chunk downloads. On the first navigation, the runtime chunk downloads once the new page has rendered, and the head then matches what the default client head shows.

## Pages with no server head

If a page has no server render, such as an SPA fallback page, call `head.load()` right after you create the head. Use the flag your server already sets for such a response. The same applies to a head that you create after hydration ended.

A load that no change started before hydration ends tells the head that no server head applies, so the runtime adopts nothing and renders the entries as they are. `head.load()` is safe to call more than once. It resolves `false` if the chunk fails to load.

## Prefetch hints

Vite loads a dynamic import's dependencies when the import runs, so by default the runtime chunk downloads on the first change. If your server adds prefetch or `modulepreload` hints for every chunk of the build, the browser downloads the runtime at once. Leave out the lazy head chunks: the runtime from `unhead/dist`, and the `lazyPlugins` chunk from `@unhead/vue/dist` if you use one.

## What loads the runtime

After hydration, the first head change loads the runtime. The runtime renders the whole head and handles every later change. These also load it:

| Trigger | When the runtime loads |
| --- | --- |
| A call the server never ran | At once. Examples: `useHead()` in `onMounted()`, or in a component that mounts after hydration. |
| A patch or dispose during hydration | At once, because the client already differs from the server. |
| `useScript()` | When it adds its script to the document. |
| `head.load()` | At once. Call it at idle to apply client only values without a change. |

A patch with the same input as before loads nothing. A reactive input resolves again when the router sets the route during hydration, and that patch changes nothing.

The lazy head compares plain objects, lists, and primitive values. It cannot read the value of a getter function or of another object, such as a promise, so a patch that holds one of these loads the runtime. A `titleTemplate` function and an event handler, such as `onload`, compare by reference.

Crawler tags, such as `og:` meta tags and JSON-LD, also wait for the first change. The `serverOnlyCrawlerTags` option of the bundler plugin drops them from the client bundle. That option ships apart from the lazy head.

## Plugins and libraries that push head tags

Plugin setup runs when you create the head. Most plugin hooks, such as a `tags:resolve` listener, take effect when the runtime loads. These hooks run before the load:

- `entries:updated` runs on each push and dispose, and on each patch that changes the input. During hydration, an in-place edit to an input does not run it, because the lazy head treats the edit as server rendered.
- `dom:beforeRender` runs on each change after hydration, because the lazy head checks for a pause. Its `tags` list is empty.
- In development, the dev check resolves the tags once after hydration, so the resolve hooks run then.

To keep plugin code out of the eager chunk, pass a loader to `lazyPlugins`. It runs together with the runtime import, and in development also for the dev check:

```ts
const head = createHead({
  lazyPlugins: () => import('@unhead/vue/plugins').then(m => [m.TemplateParamsPlugin]),
})
```

A library entry that changes on a navigation loads the runtime, as any other entry does. After hydration, each new push loads the runtime, even if its input matches an existing entry, and a dispose loads it too. If a library keeps the same input across pages, it can keep one entry and patch it: a patch with the same input loads nothing.

## Recover from a failed load

If the runtime chunk fails to load, the document keeps its current head. The `onLoadError` option receives the error, and a later change or `head.load()` tries again. A browser may keep a failed `import()` for the page, so a retry can fail too. Use `onLoadError` to recover, for example with a full page load on the next navigation. In the client entry:

```ts [src/entry-client.ts]
let reloadOnNavigation = false
const head = createHead({
  onLoadError: () => {
    reloadOnNavigation = true
  },
})

router.beforeEach((to) => {
  if (reloadOnNavigation) {
    window.location.assign(to.fullPath)
    return false
  }
})
```

## Dev warning

A tag that the client renders differently from the server waits for the first change. In development, the lazy head checks for this after hydration. It resolves the tags the client would render and compares them with the server head in the document. The check changes nothing in the document.

The console shows one warning for each tag and the component that pushed it. The lazy head keeps a list of warned tags for the browser tab, so a tag that differs on every page warns once:

```txt
[unhead] <meta name="theme-color"> differs from the server head in content. Pushed by components/ColorMode.vue. It applies on the first head change. Push the same input on the server and the client, or call head.load().
```

The check compares the title, the `meta`, `link`, `script`, `style`, and `noscript` tags, and the html and body attributes. It stays silent for a tag that the server rendered and the client does not push. It does not run if the runtime already loads. A production build holds no code for it.

## Known limitations

| Situation | What happens | What to do |
| --- | --- | --- |
| A value that the client computes differently from the server, for example one that reads `import.meta.env.SSR` or the color mode | The document keeps the server value until the first change. The dev warning names the tag. | Render the same value on both sides, or call `head.load()` after hydration. |
| `useHead()` in `onBeforeMount()` of a hydrating component, behind `import.meta.env.SSR` in `setup()`, or in a Vue plugin that pushes on install | The head counts the call as server rendered, so the tag waits for a change. | Call it in `setup()` on both sides, or in `onMounted()`. In a plugin, call `head.load()` after the call. |
| A router with no navigation hooks | Nothing pauses the load, so it can start while the next page loads. | Pause with a `dom:beforeRender` hook from your own navigation code, and call `head.render()` when the navigation ends. |
