Compiler mode makes the head cheaper on both sides of a server rendered Vue app. It has two halves:

- **The server half** compiles `useHead()` and `useSeoMeta()` calls at build time. The compiled server head renders them faster, with the same HTML.
- **The client half** keeps the Unhead DOM runtime out of the eager bundle. The server already wrote the head, so the runtime loads only when the head changes.

Each half works alone. Compiler mode is opt-in. With it off, nothing changes.

::note
Compiler mode is experimental. Its options, entry points, and compiled tag format may change in a minor release.
::

Compiler mode is for Vue apps that render on the server with `@unhead/vue` and a Vite or webpack build. If you build a framework integration, read [Compiler Mode Integration](/docs/nuxt/head/guides/framework-integration/compiler-mode).

## Entry points

The two halves mirror each other. Each entry exports `createHead()`.

| Entry point | Use it in |
| --- | --- |
| `@unhead/vue/compiled/server` | The server entry. It also exports `renderSSRHead()` and `transformHtmlTemplate()`. |
| `@unhead/vue/compiled/client` | The client entry. |

## Server half

### 1. Turn on `compile`

```ts [vite.config.ts]
import vue from '@vitejs/plugin-vue'
import { Unhead } from '@unhead/vue/vite'
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [vue(), Unhead({ compile: true })],
})
```

For webpack, call `Unhead({ compile: true }).webpack()` from `@unhead/vue/bundler`.

The production server build compiles head calls. The client build and the dev server compile nothing.

### 2. Use the compiled server head

Import `createHead()` from `@unhead/vue/compiled/server`. It takes compiled tags and normal input, and it runs every hook and plugin.

```ts [src/entry-server.ts]
import { createHead } from '@unhead/vue/compiled/server'
import { renderToString } from 'vue/server-renderer'
import { createApp } from './main'

export async function render(url: string) {
  const { app, router } = createApp()
  const head = createHead()
  app.use(head)

  await router.push(url)
  await router.isReady()

  const html = await renderToString(app)
  return { html, head }
}
```

Import `transformHtmlTemplate()` from the same entry, and use it as before:

```ts [server.ts]
import { transformHtmlTemplate } from '@unhead/vue/compiled/server'

const rendered = await render(url)
const html = transformHtmlTemplate(
  rendered.head,
  template.replace('<!--app-html-->', rendered.html),
)
```

A compiled call needs the compiled server head. On another server head, such as the one from `@unhead/vue/server`, a compiled call throws an error that says what to do.

### 3. Check the server half

Build the app and render a page. The head must match the head that the same page renders without compiler mode.

To see which calls compiled, build the server without minification. The build rewrites each compiled call to an internal `useCompiledHead()` call from `@unhead/vue/compiled/server`. Search the server chunks for it.

### What compiles

The build compiles a call when it can prove the tags from the source code. Each part that can change at runtime becomes a dynamic value.

```vue [src/pages/Post.vue]
<script setup lang="ts">
import { useHead, useSeoMeta } from '@unhead/vue'
import { computed } from 'vue'
import { useRoute } from 'vue-router'

const route = useRoute()
const title = computed(() => `Post ${route.params.slug}`)

// Compiles: `title` and the getter become dynamic values.
useHead({
  title,
  link: [{ rel: 'canonical', href: () => `https://example.com${route.path}` }],
})

// Compiles: `useSeoMeta()` is a statement on its own.
useSeoMeta({
  description: () => `Read the post ${route.params.slug}`,
  ogType: 'article',
})
</script>
```

A call compiles when all of these are true:

- It calls `useHead()`, `useServerHead()`, `useSeoMeta()`, or `useServerSeoMeta()` from `@unhead/vue`, `#imports`, `nuxt/app`, or an auto import.
- The input is an object literal. Its keys and tag lists are written out, with no spread. The input can also be a `const` that holds an object literal, if the call is the only code that reads it.
- A `useHead()` input can also be a getter, such as `useHead(() => ({ title: post.value.title }))`. The getter takes no parameters, and its last statement returns an object literal that follows the rule above. Each value of that object becomes a dynamic value.
- The only option is `head`.
- A `useSeoMeta()` call is a statement on its own. Its return value is not used.

The [`useSeoMeta()` transform](/docs/head/guides/build-plugins/seo-meta-transform) runs before compiler mode, as it runs without compiler mode. A `useSeoMeta()` call that it rewrites compiles as the `useHead()` call it wrote. So the tags keep the order of a build without compiler mode.

These calls stay as written:

| Call | Why it stays |
| --- | --- |
| `useHead(postHead)` | The input is a variable that other code reads, or that is not a `const` object literal. |
| `useHead({ titleTemplate: t => \`${t} - Site\` })` | `titleTemplate` is a function. The build warns. Use a string, such as `'%s %separator %siteName'`. |
| `useHead({ link: [{ rel: 'prev', href }] })` | A link with no `key` takes its `rel` and `href` as its identity, and the identity cannot hold a dynamic value. The build warns. Add a key, such as `key: 'prev'`. |
| `useHead({ ...base, title: 'Post' })` | The input has a spread. |
| `useHead({ meta: tags })` | The tag list is a variable. |
| `useHead(() => canonical ? { link } : {})` | The getter does not return an object literal. |
| `useHead({ title: 'Post' }, { tagPriority: 'high' })` | It has an option other than `head`. |
| `useHead({ script: [{ src: '/a.js', onload }] })` | It has an event handler. |
| `const entry = useSeoMeta({ description })` | It uses the return value of `useSeoMeta()`. |
| `useSeoMeta(() => ({ title }))` | Without compiler mode, `useSeoMeta()` renders nothing for a getter, so the call stays the same. |

The build leaves calls in CommonJS files as written. In `node_modules`, the build compiles only the runtime files of Nuxt modules, which are files under `dist/runtime/`. To compile another dependency, add it to `filter.include`:

```ts [vite.config.ts]
Unhead({
  compile: true,
  // Compiles the source files of a Nuxt layer from npm
  filter: { include: [/[\\/]node_modules[\\/]docus[\\/]/] },
})
```

### Dynamic values

A dynamic value is an expression in a compiled call that the build cannot know. The call evaluates each dynamic value once, where it stands, as it does without compiler mode. A ref, computed ref, or getter resolves once, at the first render.

A dynamic value cannot decide which tags exist or how they merge. If a call has a dynamic value in one of these places, the whole call stays as written:

| Place | Examples |
| --- | --- |
| Tag identity and order | `key`, `id`, `tagPriority`, `tagPosition`, `tagDuplicateStrategy`, `processTemplateParams` |
| Merged attributes | `class` and `style` |
| Meta identity | `name`, `property`, `http-equiv`, and `charset` |
| Link identity | `rel`, `hreflang`, `as`, and `type`. Also `href` when it identifies the link. The `href` of a canonical link, or of a link with a `key` or `id`, can be a dynamic value. |
| Script identity | `type`, `src`, `async`, and `defer`. Also inline content, unless the script has an `id` or `key`. |
| Whole tags | Any dynamic value in `titleTemplate` or `templateParams` |
| Style tags | A style attribute. Style content, unless the style has an `id` or `key` and its content comes before its attributes. |
| Packed `useSeoMeta()` keys | A dynamic value inside the object or list of a key such as `ogImage`, `articleTag`, or `robots`, when the build cannot prove the tags for each string value. A list with written out items, such as `ogImage: [{ url: image, width: 1200 }]`, usually compiles. A dynamic value for the whole key can compile. |

Every dynamic value renders the same tags as without compiler mode. A string, or a finite number other than `0`, takes the fastest path. Other values take a slower path with the same output. So do `''` and `'true'`.

## Client half

On a server rendered page, the server already wrote the right head tags. The compiled client head keeps head entries in memory and leaves those tags alone. The standard DOM runtime loads from a separate chunk when the head changes. A page that never changes its head never loads it.

The client build keeps every head call as written. `useHead()`, `useSeoMeta()`, and `useScript()` work as before.

Keep `createHead()` from `@unhead/vue/client` in these cases:

- The app renders on the client only.
- The app uses [streaming SSR](/docs/vue/head/guides/core-concepts/streaming). The compiled client head does not support streaming.

### Setup

Replace `createHead()` in the client entry:

```ts [src/entry-client.ts]
import { createHead } from '@unhead/vue/compiled/client'
import { createApp } from './main'

const { app, router } = createApp()
const head = createHead()
app.use(head)

router.isReady().then(() => {
  app.mount('#app')
  // Hydration has ended.
  head.render()

  // Block the load while a navigation runs.
  router.beforeEach(() => {
    head.blockLoad()
  })
  // Release it when the navigation ends, even if it failed.
  router.afterEach(() => {
    head.render()
  })
  router.onError(() => {
    head.render()
  })
})
```

Call `head.render()` once hydration ends. Before that call, a `useHead()` call in a hydrating component adds an entry and loads nothing. Add the navigation guards after that call, because `blockLoad()` also marks the end of hydration.

### The `load` option

`load` decides when the runtime loads on a server rendered page:

| Value | When the runtime loads |
| --- | --- |
| `'change'` | On the first head change after hydration. The default. |
| `'idle'` | At browser idle after hydration, even with no change. |

```ts
const head = createHead({ load: 'idle' })
```

With `'change'`, a page that never changes its head runs no head code after hydration. A value that the client computes differently from the server waits for the first change. With `'idle'`, the runtime applies such values at idle, as the standard client head applies them at hydration.

These also load the runtime, with either value:

| Trigger | When the runtime loads |
| --- | --- |
| A call the server never ran | At once. Examples: `useHead()` in `onMounted()`, or in a component that mounts after hydration. |
| A patch or dispose during hydration | At once, because the client already differs from the server. |
| `useScript()` | When it adds its script to the document. |
| `head.load()` | At once. |

A patch with the same input as before loads nothing. A reactive input resolves again when the router sets the route during hydration, and that patch changes nothing.

If a page is not server rendered, call `head.load()` after you create the head. `head.load()` is safe to call more than once. It resolves `false` if the chunk fails to load. The `onLoadError` option receives the error, and a later change or `head.load()` tries again.

### Block the load during navigation

A head change can start the load while the next page still loads. `head.blockLoad()` blocks the load until the next `head.render()`. If entries changed during the load block, the runtime loads at once. If nothing changed, nothing loads. A direct `head.load()` still runs during a load block.

The [`dom:beforeRender`](/docs/head/api/hooks/dom-before-render) pause also blocks the load. Call `head.render()` after you lift the pause, as the [Pause DOM Rendering](/docs/vue/head/guides/core-concepts/pausing-dom-rendering) guide shows.

### Plugins and template params

Plugin setup runs when you create the head. Plugin hooks take effect when the runtime loads.

To keep plugin code out of the eager chunk, pass a loader to `lazyPlugins`. It runs when the runtime loads:

```ts
const head = createHead({
  lazyPlugins: () => import('unhead/plugins').then(m => [m.TemplateParamsPlugin]),
})
```

### Dev warning

With the default `load: 'change'`, a tag that the client renders differently from the server waits for the first change. In development, the compiled client head checks for this after hydration. It resolves the tags the client would render and compares them with the server head in the document. The check changes nothing in the document, so the page behaves as in production.

For each client tag that is missing or different, the console shows one warning per page. The warning names the tag, the component that pushed it, and the fix:

```txt
[unhead] <meta name="theme-color"> differs from the server head in content. Pushed by components/ColorMode.vue. It applies on the first head change. Push the same input on the server and the client, set load: 'idle', or call head.load().
```

The check compares the title, the `meta`, `link`, `script`, `style`, and `noscript` tags, and the html and body attributes. It stays silent for a tag that the server rendered and the client does not push. It does not run with `load: 'idle'`. A production build holds no code for it.

## Known limitations

Check these before you ship compiler mode. Each row says what you see and what to do instead.

| Situation | What happens | What to do |
| --- | --- | --- |
| A server head from `createHead()` of `@unhead/vue/server`, as vite-ssg creates | Each compiled call throws, and the error says what to do. | Create the server head with `@unhead/vue/compiled/server`, or set `compile: false`. |
| Streaming SSR | A streamable head cannot take compiled tags, and the compiled client head does not support streaming. | Set `compile: false`, and keep `createHead()` from `@unhead/vue/client`. |
| A value that the client computes differently from the server, for example one that reads `import.meta.server` or the color mode | With `load: 'change'`, the document keeps the server value until the next head change. The dev warning names the tag. | Render the same value on both sides, set `load: 'idle'`, or call `head.load()` after hydration. |
| `useHead()` in `onBeforeMount()` of a hydrating component, behind `import.meta.client` in `setup()`, or in a client only plugin | The head counts the call as server rendered, so the tag waits for the next change. | Call it in `setup()` on both sides, or in `onMounted()`. In a plugin, call `head.load()` after the call. |
| A listener on a server render hook, such as `tags:resolve` | The server head renders on the v3 path. The HTML stays the same, but the render is slower. | Use a [tag transform](/docs/nuxt/head/guides/framework-integration/compiler-mode#change-tags-from-a-module) instead. |
| An in-place edit of `entry.input` of a compiled entry | The edit never reaches the HTML. | Call `patch()` on the entry that `push()` returned. |
| A spread, `Object.keys()`, or `JSON.stringify()` of a compiled entry | The copy has no `input`, because `input` is a getter. | Read `entry.input` directly. |
| Compiled tags created per request | After 2,048 new sets of compiled tags in one process, the render memo resets. After four resets it stays off. The output stays correct, but each render is slower. | Create compiled tags once: at build time, at module scope, or in a map on your renderer. |
| An import cycle that runs `setup()` while modules evaluate | Compiled tags are a module-scope constant. The call can reach them before they exist, and throws a `ReferenceError`. | Break the import cycle. |
| The runtime chunk fails to load | The document keeps its current head. A browser may keep the failed `import()` for the page, so a retry can fail too. | Use `onLoadError` to recover, for example with a full reload on the next navigation. |
| A router with no navigation hooks | Nothing can block the load, so it can start while the next page loads. | Call `head.blockLoad()` and `head.render()` from your own navigation code. |
