The compiled server head renders the head of a server rendered Vue app faster. The HTML stays byte for byte the same.

The build compiles your `useHead()` and `useSeoMeta()` calls to compiled tags. The server head keeps a memo of the HTML for each sequence of compiled tags. A request that renders the same head skips the normalize, dedupe, and sort work.

The feature is opt-in. With it off, nothing changes.

::note
The compiled server head is experimental. Its options, entry points, and compiled tag format may change in a minor release.
::

## What it gains

The gain depends on how much of a request the head takes. It is largest on an app with little else to render.

Best case, measured on a bare Nuxt 5 nightly app with no modules:

| Route | Head render, off | Head render, on | Requests per second |
| --- | --- | --- | --- |
| Static page, 22 to 24 tags | 82 to 89 µs | 5 µs | +39 to 47% |
| Static page, 51 tags | 106 µs | 5 µs | +55% |
| Page with values from route params | 83 µs | 10 to 11 µs | +34 to 35% |

The head render is one real render per request, median of 1,000 requests. Requests per second come from autocannon with the server on one core. Off, the head render took about 20% of request CPU. The SSR HTML was identical off and on, on every route.

The gain is fragile. One call that stays as written moves the page off the memo. In an earlier run, one keyless JSON-LD script did that, and the gain on that page fell to 5%.

On real sites with released Nuxt modules, the gain today is 0. SEO and image modules add render hooks, and a render hook sends every page to the full runtime. On those sites, head rendering took under 1% of a request anyway.

## Turn it on

1. Turn on `compile` in the Vite plugin:

    ```ts [vite.config.ts]
    import { Unhead } from '@unhead/vue/vite'
    import vue from '@vitejs/plugin-vue'
    import { defineConfig } from 'vite'

    export default defineConfig({
      plugins: [vue(), Unhead({ compile: true })],
    })
    ```

    The production server build compiles head calls. The client build and the dev server leave every call as written.

    Only a Vite build compiles. Another bundler warns once and leaves every call as written.

2. Create the server head from `@unhead/vue/compiled/server`:

    ```ts [src/entry-server.ts]
    import { createHead } from '@unhead/vue/compiled/server'
    import { renderToString } from 'vue/server-renderer'
    import { createApp } from './main'

    export async function render(url: string) {
      const { app, router } = createApp()
      const head = createHead()
      app.use(head)
      await router.push(url)
      await router.isReady()
      return { html: await renderToString(app), head }
    }
    ```

3. Render the head as before. `transformHtmlTemplate()` and `head.render()` work with the compiled server head:

    ```ts [server.ts]
    import { transformHtmlTemplate } from '@unhead/vue/server'

    const { html, head } = await render(url)
    const page = transformHtmlTemplate(head, template.replace('<!--app-html-->', html))
    ```

A compiled call needs the compiled server head. On another server head, a compiled call throws an error that says what to do.

## See the tier

Each render takes one of three tiers. All three give the same HTML.

| Tier | What renders | When |
| --- | --- | --- |
| `Memo` | The memo of the HTML, with the dynamic values put in | Every entry is compiled tags with no options, and no listener is on a render hook |
| `Fast` | Compiled tags without the full runtime | Some entries are head input, or have options |
| `Full` | The full runtime | A listener is on a render hook, or an option needs the runtime |

Call `getRenderTier()` before the render to see the tier and the reason:

```ts
import { getRenderTier } from 'unhead/compiled/server'

const tier = getRenderTier(head)
// { _tag: 'Memo' }
// { _tag: 'Fast', reason: '1 entry holds head input or has entry options' }
// { _tag: 'Full', reason: 'a listener on the tags:afterResolve hook' }
```

`Memo` means the head can use the memo. A value that could change how the tags merge or escape still takes the `Fast` tier for that render, with the same HTML.

## What lowers the tier

| Cause | Tier | What to do |
| --- | --- | --- |
| A listener on a render hook: `entries:resolve`, `entries:normalize`, any `tags:` hook, `ssr:beforeRender`, `ssr:render`, or `ssr:rendered` | `Full` | Remove the listener, or make it a [tag transform](#change-tags-from-a-module). Most come from modules, so this needs a module change. |
| A plugin other than the native ones that adds a render hook | `Full` | As above. |
| A native plugin in object form, such as `head.use(InferSeoMetaPlugin()(head))` | `Full` | Pass the plugin itself: `head.use(InferSeoMetaPlugin())`. |
| A custom `tagWeight`, or your own function in `propResolvers` | `Full` | Use the default weights. |
| A call that stays as written, so its entry holds head input | `Fast` | See [what compiles](#what-compiles). The build warns for the common fixes. |
| Compiled tags pushed with entry options, such as `tagPriority` | `Fast` | Push them with no options. |
| `InferSeoMetaPlugin` with an `ogTitle` or `ogDescription` function | `Fast` | Remove the function, or accept the `Fast` tier. |
| A tag transform with no `memoKey`, or whose `memoKey` returns `null` | `Fast` | See [keep the memo](#keep-the-memo). |
| Compiled tags created per request, until the memo turns off | `Fast` | Create compiled tags once. See [limitations](#limitations). |

Two plugins run natively and keep the memo: `TemplateParamsPlugin` and `InferSeoMetaPlugin`. Their behaviour does not change.

## Change tags from a module

A module that changes the resolved tags, for example to add an `og:url` from the canonical link, declares a tag transform. A `tags:` hook sends every render to the `Full` tier. A tag transform keeps the `Fast` tier. With a [`memoKey`](#keep-the-memo), it keeps the `Memo` tier.

```ts
import { defineTagTransform } from 'unhead/plugins'

head.use(defineTagTransform({
  key: 'my-module:og-url',
  transform: (tags) => {
    const canonical = tags.find(tag => tag.tag === 'link' && tag.props.rel === 'canonical')
    return canonical && !tags.some(tag => tag.props.property === 'og:url')
      ? [...tags, { tag: 'meta', props: { property: 'og:url', content: canonical.props.href } }]
      : tags
  },
}))
```

- `transform` gets the resolved tags: dedupe, sort, the title template, and template params ran. It returns the tags to render.
- `transform` reads only `tags` and its context. The tags are copies for that render, so it can change a tag in place or return a new one.
- `defineTagTransform()` is required. It adds the `tags:afterResolve` hook that runs the transform on the full runtime and on the client, so the output is the same on every tier.
- Transforms run in the order their plugins register, in the place of their `tags:afterResolve` hook.
- If the plugin has its own `tags:afterResolve` hook, that hook runs first, and the head renders on the full runtime.

### Keep the memo

A transform with no `memoKey` never uses the memo. The head takes the `Fast` tier, and the transform sees the real values on each render.

To use the memo, add a `memoKey`. The memo then runs the transform one time for each sequence of compiled tags, and holds the output. A `memoKey` states two things:

- It returns everything else the output depends on, as a string. The memo holds one output for each key. If the output depends on the tags only, return `''`.
- The transform copies or drops text it did not make, and never tests it. In the memo, a dynamic value reaches the transform as a token, so a test of it gives a wrong answer.

The example above copies the canonical href and tests no text. So it can use the memo with one more line in its plugin: `memoKey: () => ''`.

If a transform must test a dynamic value in some heads, `memoKey` returns `null` for those heads. Such a head takes the `Fast` tier.

### A host name known only at request time

A module that makes URLs absolute may know the site URL only from the request. Define the plugin for each request, and return the resolved site URL from `memoKey`:

```ts
import { defineTagTransform } from 'unhead/plugins'

function absoluteUrls(siteUrl: string) {
  return defineTagTransform({
    key: 'my-module:absolute-urls',
    memoKey: () => siteUrl,
    transform: tags => tags.map(tag => tag.tag === 'link' && tag.props.rel === 'canonical'
      ? { ...tag, props: { ...tag.props, href: siteUrl + tag.props.href } }
      : tag),
  })
}
```

A page holds the memos of 16 to 32 memo keys, and drops the keys that no recent render used. So requests with unknown `Host` headers cannot grow the memo without limit, and a host in use keeps its memo.

## Read an entry from a module

A compiled entry holds compiled tags, and no head input. A module that reads `entry.input`, for example to find the page title, reads every entry with `readEntry()`:

```ts
import { readEntry } from 'unhead/compiled'

for (const entry of head.entries.values()) {
  const { input, seoMeta } = readEntry(entry, head)
  if (seoMeta) {
    const description = input.meta?.find(meta => meta.name === 'description')?.content
    console.log(input.title, description)
  }
}
```

`readEntry()` reads compiled tags and head input, on the compiled server head and on a head from `unhead/server`. It does not render. It returns:

| Field | Value |
| --- | --- |
| `input` | The entry as head input. Refs and getters are resolved, and the flat meta of a `useSeoMeta()` call is unpacked to meta tags. Treat it as read only: static input is the object the entry holds. |
| `seoMeta` | `true` for an entry from a `useSeoMeta()` call, compiled or not. |
| `compiled` | `true` when the entry holds compiled tags. |
| `dynamicPaths` | The path of each dynamic value in `input`, such as `title` or `meta.0.content`. `undefined` when every value is static, and for head input. |

On the compiled server head, the value function of an entry runs once, at the first read or the first render.

A dynamic value can change on each render, and the memo holds a token in its place. So a [tag transform](#keep-the-memo) that must test a value checks `dynamicPaths` in its `memoKey`. A static relative image URL keeps the memo, and a dynamic one returns `null`:

```ts
const { input, dynamicPaths } = readEntry(entry, head)
const testsDynamicValue = input.meta?.some((meta, i) => meta.property === 'og:image' && dynamicPaths?.includes(`meta.${i}.content`))
```

With `compile` on, the server build marks each `useSeoMeta()` call, so `seoMeta` is `true` for it. A module that pushes compiled tags for such a call sets the marker itself. The entry keeps the memo:

```ts
head.push(compiledTags, { seoMeta: true })
```

`readEntry()` and the `seoMeta` option are experimental. They may change in a minor release.

## What compiles

The build compiles a call when it can prove the tags from the source code. Each part that can change at runtime becomes a dynamic value.

```vue [src/pages/Post.vue]
<script setup lang="ts">
import { useHead, useSeoMeta } from '@unhead/vue'
import { useRoute } from 'vue-router'

const route = useRoute()
const title = `Post ${route.params.slug}`

// Compiles: `title` and the JSON-LD content become dynamic values
useHead({
  title,
  link: [{ rel: 'canonical', href: `https://example.com${route.path}` }],
  script: [{ type: 'application/ld+json', innerHTML: JSON.stringify({ headline: title }) }],
})

// Compiles: the call is a statement on its own
useSeoMeta({ description: `Read the post ${route.params.slug}`, ogType: 'article' })
</script>
```

A call compiles when all of these are true:

- It calls `useHead()`, `useServerHead()`, `useSeoMeta()`, or `useServerSeoMeta()` from `@unhead/vue` or `nuxt/app`. An auto import needs [the `autoImports` option](#auto-imports).
- The input is an object literal with written out keys and tag lists, and no spread. A `const` that holds an object literal also works, if the call is its only reader.
- A `useHead()` input can be a getter with no parameters whose last statement returns an object literal.
- The only option is `head`.
- A `useSeoMeta()` call is a statement on its own.

These calls stay as written:

| Call | Why | Fix |
| --- | --- | --- |
| `useHead(postHead)` | The input is a variable that other code reads | Write the object in the call |
| `useHead({ titleTemplate: t => \`${t} - Site\` })` | `titleTemplate` is a function. The build warns. | Use a string, such as `'%s %separator %siteName'` |
| `useHead({ link: [{ rel: 'prev', href }] })` | A link with no `key` uses `rel` and `href` as its identity. The build warns. | Add a key, such as `key: 'prev'` |
| `useHead({ script: [{ innerHTML: code }] })` | An inline script with no `key` uses its content as its identity | Add a `key` |
| `useHead({ ...base, title: 'Post' })` | The input has a spread | Write out the keys |
| `useHead({ title: 'Post' }, { tagPriority: 'high' })` | It has an option other than `head` | Remove the option |
| `useHead({ title: 'Post' })` with no import | The build cannot see what an auto import stands for | Name it in [`autoImports`](#auto-imports) |

A JSON script with no `key`, such as JSON-LD, compiles even when its content is a dynamic value. Its weight never depends on its content. At render, the memo checks that no other tag of the head has the same content. If one has, that render takes the `Fast` tier.

A dynamic value cannot decide which tags exist or how they merge. A dynamic value in `key`, `id`, `tagPriority`, `class`, `style`, a meta `name` or `property`, or a link `rel` keeps the whole call as written.

### Auto imports

The build cannot see what an auto import stands for. A project can replace `useHead` with its own function. So a call with no import stays as written. So does a call that imports from `#imports`.

To compile these calls, name the auto imports that are the head composables of `@unhead/vue`:

```ts [vite.config.ts]
Unhead({ compile: { autoImports: ['useHead', 'useSeoMeta'] } })
```

If a name stands for another function, leave it out of the list. A compiled call never runs that function.

## Compiled tags without the bundler

A framework can compile static input itself with `compileTags()`. Compile once, at build time or at module scope, never per request.

```ts
import { compileTags, createHead, dynamicValue } from 'unhead/compiled/server'

const result = compileTags({ title: dynamicValue(0), meta: [{ name: 'description', content: 'About' }] }, { valueCount: 1 })
const head = createHead()
if (result._tag === 'Ok')
  head.push(result.tags, { values: ['Page'] })
```

`compileTags()` never throws. For input it cannot prove, it returns `{ _tag: 'Err', reason }`, and you push the input as head input.

## Limitations

| Situation | What happens | What to do |
| --- | --- | --- |
| Released Nuxt SEO modules | They add render hooks, so every page takes the `Full` tier. The gain is 0. | Nothing yet. The modules must move their render hooks to [tag transforms](#change-tags-from-a-module) first. |
| Streaming SSR | A streamable head cannot take compiled tags | Set `compile: false` |
| A server head from `@unhead/vue/server`, as vite-ssg creates | Each compiled call throws | Create the head from `@unhead/vue/compiled/server`, or set `compile: false` |
| An in-place edit of `entry.input` of a compiled entry | The edit never reaches the HTML | Call `patch()` on the entry that `push()` returned |
| Compiled tags created per request | After 2,048 new sequences in one process, the memo resets. After four resets it stays off: the server warns once, and `getRenderTier()` reports `Fast` with the reason. | Create compiled tags once |
| A bundler other than Vite, such as webpack | Nothing compiles. The build warns once. | Build with Vite, or remove `compile` |
| Frameworks other than Vue | The bundler compiles `@unhead/vue` calls only. The build warns once. | Use `compileTags()` with `unhead/compiled/server` |
