The compiled server head renders the head of a server rendered Vue app faster. The HTML stays byte for byte the same.

The build compiles your `useHead()` and `useSeoMeta()` calls to compiled tags. The server head keeps a memo of the HTML for each set of compiled tags. A request that renders the same head skips the normalize, dedupe, and sort work.

The feature is opt-in. With it off, nothing changes.

::note
The compiled server head is experimental. Its options, entry points, and compiled tag format may change in a minor release.
::

## What it gains

The gain depends on how much of a request the head takes. It is largest on an app with little else to render.

Best case, measured on a bare Nuxt 5 nightly app with no modules:

| Route | Head render, off | Head render, on | Requests per second |
| --- | --- | --- | --- |
| Static page, 22 to 24 tags | 82 to 89 µs | 5 µs | +39 to 47% |
| Static page, 51 tags | 106 µs | 5 µs | +55% |
| Page with values from route params | 83 µs | 10 to 11 µs | +34 to 35% |

The head render is one real render per request, median of 1,000 requests. Requests per second come from autocannon with the server on one core. Off, the head render took about 20% of request CPU. The SSR HTML was identical off and on, on every route.

The gain is fragile. One call that stays as written moves the page off the memo. In an earlier run, one keyless JSON-LD script did that, and the gain on that page fell to 5%.

On real sites with released Nuxt modules, the gain today is 0. SEO and image modules add render hooks, and a render hook sends every page to the full runtime. On those sites, head rendering took under 1% of a request anyway.

## Turn it on

1. Turn on `compile` in the Vite plugin:

    ```ts [vite.config.ts]
    import { Unhead } from '@unhead/vue/vite'
    import vue from '@vitejs/plugin-vue'
    import { defineConfig } from 'vite'

    export default defineConfig({
      plugins: [vue(), Unhead({ compile: true })],
    })
    ```

    For webpack, call `Unhead({ compile: true }).webpack()` from `@unhead/vue/bundler`. The production server build compiles head calls. The client build and the dev server leave every call as written.

2. Create the server head from `@unhead/vue/compiled/server`:

    ```ts [src/entry-server.ts]
    import { createHead } from '@unhead/vue/compiled/server'
    import { renderToString } from 'vue/server-renderer'
    import { createApp } from './main'

    export async function render(url: string) {
      const { app, router } = createApp()
      const head = createHead()
      app.use(head)
      await router.push(url)
      await router.isReady()
      return { html: await renderToString(app), head }
    }
    ```

3. Render the head as before. `transformHtmlTemplate()` and `head.render()` work with the compiled server head:

    ```ts [server.ts]
    import { transformHtmlTemplate } from '@unhead/vue/server'

    const { html, head } = await render(url)
    const page = transformHtmlTemplate(head, template.replace('<!--app-html-->', html))
    ```

A compiled call needs the compiled server head. On another server head, a compiled call throws an error that says what to do.

## See the tier

Each render takes one of three tiers. All three give the same HTML.

| Tier | What renders | When |
| --- | --- | --- |
| `Memo` | The memo of the HTML, with the dynamic values put in | Every entry is compiled tags with no options, and no foreign hook listens |
| `Fast` | Compiled tags without the full runtime | Some entries are normal input, or have options |
| `Full` | The full v3 runtime | A foreign hook listens, or an option needs the runtime |

Call `getRenderTier()` before the render to see the tier and the reason:

```ts
import { getRenderTier } from 'unhead/compiled/server'

const tier = getRenderTier(head)
// { _tag: 'Memo' }
// { _tag: 'Fast', reason: '1 entry is not compiled tags with no options' }
// { _tag: 'Full', reason: 'a listener on the tags:afterResolve hook' }
```

`Memo` means the head can use the memo. A value that could change how the tags merge or escape still takes the `Fast` path for that render, with the same HTML.

## What blocks the fast path

| Cause | Tier | What to do |
| --- | --- | --- |
| A listener on a render hook: `entries:resolve`, `entries:normalize`, any `tags:` hook, `ssr:beforeRender`, `ssr:render`, or `ssr:rendered` | `Full` | Remove the listener. Most come from modules, so this needs a module change. |
| A plugin other than the native ones that adds a render hook | `Full` | As above. |
| A native plugin in object form, such as `head.use(InferSeoMetaPlugin()(head))` | `Full` | Pass the plugin itself: `head.use(InferSeoMetaPlugin())`. |
| A custom `tagWeight` or a dynamic prop resolver | `Full` | Use the default weights. |
| A call that stays as written (a loose entry) | `Fast` | See [what compiles](#what-compiles). The build warns for the common fixes. |
| Compiled tags pushed with entry options, such as `tagPriority` | `Fast` | Push them with no options. |
| `InferSeoMetaPlugin` with an `ogTitle` or `ogDescription` function | `Fast` | Remove the function, or accept the `Fast` tier. |

Two plugins run natively and keep the memo: `TemplateParamsPlugin` and `InferSeoMetaPlugin`. Their behaviour does not change.

## What compiles

The build compiles a call when it can prove the tags from the source code. Each part that can change at runtime becomes a dynamic value.

```vue [src/pages/Post.vue]
<script setup lang="ts">
import { useHead, useSeoMeta } from '@unhead/vue'
import { useRoute } from 'vue-router'

const route = useRoute()
const title = `Post ${route.params.slug}`

// Compiles: `title` and the JSON-LD content become dynamic values
useHead({
  title,
  link: [{ rel: 'canonical', href: `https://example.com${route.path}` }],
  script: [{ type: 'application/ld+json', innerHTML: JSON.stringify({ headline: title }) }],
})

// Compiles: the call is a statement on its own
useSeoMeta({ description: `Read the post ${route.params.slug}`, ogType: 'article' })
</script>
```

A call compiles when all of these are true:

- It calls `useHead()`, `useServerHead()`, `useSeoMeta()`, or `useServerSeoMeta()` from `@unhead/vue` or `nuxt/app`. An auto import needs [the `autoImports` option](#auto-imports).
- The input is an object literal with written out keys and tag lists, and no spread. A `const` that holds an object literal also works, if the call is its only reader.
- A `useHead()` input can be a getter with no parameters whose last statement returns an object literal.
- The only option is `head`.
- A `useSeoMeta()` call is a statement on its own.

These calls stay as written:

| Call | Why | Fix |
| --- | --- | --- |
| `useHead(postHead)` | The input is a variable that other code reads | Write the object in the call |
| `useHead({ titleTemplate: t => \`${t} - Site\` })` | `titleTemplate` is a function. The build warns. | Use a string, such as `'%s %separator %siteName'` |
| `useHead({ link: [{ rel: 'prev', href }] })` | A link with no `key` uses `rel` and `href` as its identity. The build warns. | Add a key, such as `key: 'prev'` |
| `useHead({ script: [{ innerHTML: code }] })` | An inline script with no `key` uses its content as its identity | Add a `key` |
| `useHead({ ...base, title: 'Post' })` | The input has a spread | Write out the keys |
| `useHead({ title: 'Post' }, { tagPriority: 'high' })` | It has an option other than `head` | Remove the option |
| `useHead({ title: 'Post' })` with no import | The build cannot see what an auto import stands for | Name it in [`autoImports`](#auto-imports) |

A JSON script with no `key`, such as JSON-LD, compiles even when its content is a dynamic value. Its weight never depends on its content. At render, the memo checks that no other tag of the head has the same content. If one has, that render takes the `Fast` path.

A dynamic value cannot decide which tags exist or how they merge. A dynamic value in `key`, `id`, `tagPriority`, `class`, `style`, a meta `name` or `property`, or a link `rel` keeps the whole call as written.

### Auto imports

The build cannot see what an auto import stands for. A project can replace `useHead` with its own function. So a call with no import stays as written. So does a call that imports from `#imports`.

To compile these calls, name the auto imports that are the head composables of `@unhead/vue`:

```ts [vite.config.ts]
Unhead({ compile: { autoImports: ['useHead', 'useSeoMeta'] } })
```

If a name stands for another function, leave it out of the list. A compiled call never runs that function.

## Compiled tags without the bundler

A framework can compile static input itself with `compileTags()`. Compile once, at build time or at module scope, never per request.

```ts
import { compileTags, createHead, dynamicValue } from 'unhead/compiled/server'

const result = compileTags({ title: dynamicValue(0), meta: [{ name: 'description', content: 'About' }] }, { dynamicValues: 1 })
const head = createHead()
if (result._tag === 'Ok')
  head.push(result.tags, { values: ['Page'] })
```

`compileTags()` never throws. For input it cannot prove, it returns `{ _tag: 'Bail', reason }`, and you push the input as normal input.

## Limitations

| Situation | What happens | What to do |
| --- | --- | --- |
| Released Nuxt SEO modules | They add render hooks, so every page takes the `Full` tier. The gain is 0. | Nothing yet. The modules must drop their render hooks first. |
| Streaming SSR | A streamable head cannot take compiled tags | Set `compile: false` |
| A server head from `@unhead/vue/server`, as vite-ssg creates | Each compiled call throws | Create the head from `@unhead/vue/compiled/server`, or set `compile: false` |
| An in-place edit of `entry.input` of a compiled entry | The edit never reaches the HTML | Call `patch()` on the entry that `push()` returned |
| Compiled tags created per request | After 2,048 new sets in one process, the memo resets. After four resets it stays off. | Create compiled tags once |
| Frameworks other than Vue | The bundler compiles `@unhead/vue` calls only | Use `compileTags()` with `unhead/compiled/server` |
